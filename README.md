# Диалоговый модуль расчёта Индекса уязвимости

Программный модуль для автоматизированного сбора данных и расчёта
**Индекса уязвимости (ИУ)** высокогорных, отдалённых и приграничных
населённых пунктов Кыргызской Республики — согласно техническому
заданию [`ТЗ_Modul_Indeх_08072026.md`](./ТЗ_Modul_Indeх_08072026.md) и
утверждённой методике расчёта (раздел 4 ТЗ).

Ключевая особенность модуля — **диалоговый (вопрос-ответ) сценарий**
сбора исходных показателей: по каждому из 17 показателей методики
оператор может выбрать, откуда взять значение — автоматически из
цепочки источников, из конкретного источника, вручную или как
документированное допущение — и сразу увидеть, какой балл будет
присвоен и как это повлияет на итоговый Индекс.

## Как методика реализована в коде

Формула ИУ, состав компонентов (GEO, ACC, DEM, SERV, INFRA, ECO, ECON),
их веса и балльные интервалы **не зашиты в код**, а полностью описаны в
YAML-конфигурации [`vulnerability_index/config/methodology_v1.yaml`](vulnerability_index/config/methodology_v1.yaml)
— построчное соответствие разделу 4 ТЗ. Расчётный движок
([`vulnerability_index/methodology.py`](vulnerability_index/methodology.py))
читает эту конфигурацию и:

- присваивает баллы показателям по числовым интервалам (`numeric_thresholds`)
  или справочникам вариантов (`options`);
- считает значение каждого компонента как средневзвешенное входящих в
  него показателей;
- считает итоговый ИУ = 0,20·GEO + 0,30·ACC + 0,10·DEM + 0,10·SERV +
  0,10·INFRA + 0,10·ECO + 0,10·ECON;
- присваивает категорию уязвимости по настраиваемым порогам (пороги
  явно помечены как **не утверждённые** — методика не фиксирует точные
  числа, см. п. 4.9, 13 ТЗ);
- поддерживает **версионирование**: `MethodologyRepository` хранит
  несколько файлов `methodology_v*.yaml` с разными `effective_date` и
  умеет выбрать версию, действовавшую на любую дату — для пересчёта
  «на дату» (п. 4.10 ТЗ). Чтобы ввести новую версию методики, создайте
  `methodology_v2.yaml` — старая версия останется доступной.

Методолог может поменять веса, интервалы, пороги категорий или добавить
новый показатель, отредактировав YAML — без изменения кода.

## Источники данных

Реализована абстракция источника данных (`DataSource`,
[`vulnerability_index/datasources/`](vulnerability_index/datasources/))
и цепочка с автоматическим fallback (`DataSourceChain`), покрывающие все
способы получения данных из п. 5.9 ТЗ:

| Коннектор | Что имитирует / к чему подключается |
|---|---|
| `ManualInputSource` | Ручной ввод оператором (ядро диалога) — с указанием документа-основания |
| `TableDataSource` | Периодическая выгрузка файлов (CSV/XLSX) из ведомственных систем |
| `RestApiDataSource` | REST API существующих автоматизированных государственных ИС |
| `NscOpenDataSource` | Открытые данные портала **Национального статистического комитета КР** (сайт НСК, stat.kg): скачивает и кэширует XLSX/CSV-выгрузку; при недоступности сайта — локальный резервный файл |
| `OpenElevationSource` | Открытый интернет-геосервис (Open-Elevation / SRTM) — пример геопространственного источника из п. 5.1 ТЗ |

Для каждого показателя настраивается **цепочка** источников с приоритетом
(`vulnerability_index/source_factory.py` — пример готовой сборки для
демонстрации на синтетических данных из `data/demo/`). Если верхний по
приоритету источник недоступен, модуль автоматически переходит к
следующему и фиксирует все попытки (для аудита, п. 5.10 ТЗ). Если все
источники недоступны — диалог предлагает оператору ввести значение
вручную или задать **документируемое допущение** (п. 4.10 ТЗ: ближайшие
доступные значения / данные смежных территорий / геоинформационный
анализ / экспертная оценка) либо явно пометить показатель «нет данных»
(с уведомлением ответственного лица).

> В `data/demo/` находятся **синтетические** демонстрационные выгрузки
> (не официальные данные) для 5 примерных населённых пунктов — см.
> [`data/demo/README.md`](data/demo/README.md). Реальные реквизиты
> доступа к ведомственным системам и порталу НСК уточняются на этапе
> обследования (раздел 13 ТЗ) и подставляются в `source_factory.py`
> (или отдельный конфиг) без изменения остального кода.

## Установка

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pip install -e .
```

Требуется Python 3.10+.

## Использование

### Интерактивный диалог расчёта Индекса

```bash
python -m vulnerability_index.cli dialog
# или сразу для конкретного населённого пункта:
python -m vulnerability_index.cli dialog --settlement KG-001
```

Модуль последовательно проведёт по всем 7 компонентам и 17 показателям,
на каждом шаге предложит способ получения данных, покажет присвоенный
балл и в конце — полную детализацию расчёта ИУ с категорией уязвимости.
Результат сохраняется в `data/results/<код_нп>/` с историей расчётов.

### Просмотр действующей методики

```bash
python -m vulnerability_index.cli show-methodology
python -m vulnerability_index.cli show-methodology --date 2026-06-01   # версия, действовавшая на дату
```

### Реестр населённых пунктов

```bash
python -m vulnerability_index.cli list-settlements
```

### Полный неинтерактивный пересчёт (батч/ETL-режим)

Соответствует требованию п. 4.10/6.2 ТЗ о полном автоматическом
пересчёте Индекса по всем населённым пунктам (не реже раза в 3 года):

```bash
python -m vulnerability_index.cli recalc                 # по всем н.п.
python -m vulnerability_index.cli recalc --settlement KG-001
python -m vulnerability_index.cli recalc --date 2026-01-01
```

В батч-режиме показатели собираются только по настроенным цепочкам
источников (без вопросов оператору); недоступные показатели помечаются
«нет данных» и требуют последующей ручной проверки/допущения через
диалоговый режим.

## Архитектура модуля

```
vulnerability_index/
  config/methodology_v1.yaml   — конфигурация методики (версия 1, раздел 4 ТЗ)
  models.py                    — доменные модели (Settlement, DataValue, IndexResult...)
  methodology.py                — расчётный движок + версионирование методики
  datasources/                  — коннекторы источников + цепочка fallback
    base.py, manual.py, file_source.py, api_source.py,
    nsc_source.py, web_source.py, chain.py
  settlements.py                — эталонный реестр населённых пунктов (п. 5.11 ТЗ)
  source_factory.py             — пример сборки цепочек источников "из коробки"
  dialog.py                     — диалоговый модуль (вопрос-ответ)
  batch.py                      — неинтерактивный полный пересчёт (ETL-режим)
  storage.py                    — хранение результатов, истории, верификации
  cli.py                        — командный интерфейс (dialog/recalc/...)
data/
  reference/settlements.csv     — демо-реестр из 5 населённых пунктов
  demo/                         — синтетические демо-выгрузки ведомств
  cache/, raw/, results/        — рабочие каталоги модуля (создаются автоматически)
tests/                          — pytest-тесты (методика, источники, диалог, хранение, батч)
```

Модульная архитектура соответствует требованию п. 7.1 ТЗ: слой сбора
данных (коннекторы), расчётный движок и слой хранения/CLI разделены и
могут быть заменены независимо (например, `cli.py`/`dialog.py` — на
веб-интерфейс, использующий тот же `IndexDialog`/`Methodology` API).

## Тесты

```bash
pytest -q
```

110+ тестов покрывают: балльные шкалы и формулы всех 7 компонентов по
контрольным значениям из методики, работу и fallback всех источников
данных (включая сетевые сбои НСК/API — через мок), сценарии диалога
(авто/вручную/допущение/«нет данных»), хранение и историю расчётов,
неинтерактивный пересчёт по реестру.

## Открытые вопросы / что нужно уточнить для промышленного внедрения

Как и указано в разделе 13 ТЗ, до промышленного внедрения требуется:

1. Утвердить точные числовые пороги категорий уязвимости (сейчас в
   `methodology_v1.yaml` — временная заглушка с явным флагом
   `categories.approved: false`).
2. Получить реквизиты доступа (API/контакты) к реальным ведомственным
   ИС и порталу НСК и заменить демонстрационные `data/demo/*.csv` и
   заглушечные URL в `source_factory.py` на реальные подключения.
3. Добавить полноценную аутентификацию/RBAC, очередь задач для
   планового сбора данных и веб-интерфейс/дашборды — в этой версии
   реализован основной диалоговый модуль расчёта и интеграционный слой
   (разделы 4–6 ТЗ), административный веб-UI (раздел 6.4, 7.5 ТЗ) не
   входит в объём текущей реализации.
